System owner’s guide

This guide is separate from app training. It is for the officers who own the Heroku account, billing, deployment, and member data. You can also open docs/system-guide.html from a downloaded repository before the website is running. Use your browser’s Print option to save a PDF.

Accounts and handover

A Heroku app is the hosted website. Its web dyno runs the app; its Postgres add-on holds the records. A GitHub repository stores the code. Google provides member sign-in. These are separate accounts and permissions.

  1. Use the organization’s Heroku account or team, with an agreed billing owner and named officers who can manage the app. Keep at least one recovery contact current.
  2. Keep access to the private GitHub repository, the Google Cloud project that owns sign-in, and the organization’s password manager.
  3. Record the production and staging app names, live URLs, deployed Git commit, plan names, backup schedule, and Google client owner in the private handover record.
  4. Hand over those accounts before a departing officer loses access. The app’s Manager role does not grant Heroku, Google Cloud, or GitHub access.

Config Vars are private settings, including credentials. Do not put their values, database URLs, backup download links, or real member records in commits, screenshots, PRs, or group chats.

Install and deploy into the organization’s account

You need an approved billing plan, repository access, and the sign-in client’s private settings. Install Git and the Heroku CLI. Open a terminal (PowerShell on Windows).

  1. 1. Create app
  2. 2. Add database
  3. 3. Set sign-in
  4. 4. Deploy code
  5. 5. Test and hand over
  1. Download the repository, then sign into Heroku: 
    git clone https://github.com/FA26-CSCE431-software-engineering/PT-502.git
cd PT-502
heroku login
  2. In Heroku Dashboard, choose the organization/team, then New → Create new app. Pick a unique name and region. For an existing app, use its name instead of creating a second one. Connect this checkout: 
    heroku git:remote --app YOUR-APP
  3. Open the app’s Resources tab and add Heroku Postgres. Confirm the selected plan and cost before provisioning. For a small new app, the equivalent CLI command is: 
    heroku addons:create heroku-postgresql:essential-0 --app YOUR-APP
    Do not add another database if the app already has its intended one. Heroku supplies DATABASE_URL automatically.
  4. Open Settings → Reveal Config Vars. Set RAILS_ENV to production, RAILS_MASTER_KEY to the matching repository credentials key from the password manager, and GOOGLE_OAUTH_CLIENT_ID / GOOGLE_OAUTH_CLIENT_SECRET to the organization’s Google web client. Use the existing matching master key, not a newly generated unrelated one. The key file is intentionally excluded from Git.
  5. Use heroku apps:info --app YOUR-APP to find the exact Web URL. In the Google Cloud client’s authorized redirect URIs, add that URL followed by /members/auth/google_oauth2/callback. Remove a trailing slash from the base URL first. Add staging’s exact URL too if testing there. Do not guess the Heroku URL from the app name. Members must select @tamu.edu accounts.
  6. In Dashboard → Deploy, use the Heroku Ruby buildpack and connect the repository’s reviewed main branch. Start with manual deployments. Or deploy the reviewed checkout with: 
    git fetch origin
git switch main
git pull --ff-only origin main
git push heroku main
    The repository’s Procfile starts Puma and runs database migrations in the release phase. Wait for both the build and release to succeed. Assets are compiled during the Ruby build.
  7. In Resources, enable one web dyno on the approved plan. For Basic: 
    heroku ps:scale web=1:basic --app YOUR-APP
    This starts billable service. Do not enable a worker or extra databases just because Rails lists those gems; this app currently uses no background job workflow.
  8. For a genuinely new empty organization database, create the initial Manager and default point types. Replace the example email and names with the agreed real owner: 
    heroku run "bundle exec rake system:bootstrap EMAIL=owner@tamu.edu FIRST_NAME=First LAST_NAME=Last" --app YOUR-APP
    This task can be safely repeated for the same initial owner. It stops if another Manager already exists. It does not award points or mark the profile complete. The existing db:seed task assigns the original project owner as Manager; do not use it to bootstrap a different organization.
  9. Choose Open app or run heroku open --app YOUR-APP. Sign in as the owner, finish the profile, and check Members and Point requirements. Test a member’s sign-in and check that officer tools are hidden from them. Visit /up for the health response, then /help for training.

Before inviting members, rehearse the full process in a separate staging app with fictional data. This guide documents deployment; it does not itself provision or charge for a Heroku account.

Reference: Heroku’s Rails setup guide and release phase.

Run a local copy

A local copy is useful for checking changes without touching club records. Install Ruby matching .ruby-version (3.4.6 at this review), Bundler, and PostgreSQL. On Windows, this repository’s Ruby workflow can run inside WSL Ubuntu; keep the browser on Windows and open localhost.

  1. Download the repository as above. Create a local PostgreSQL login called pt502 with permission to create databases, or use another local login with that permission.
  2. Create an untracked .env in the repository directory with DATABASE_USER, DATABASE_PASSWORD, and DATABASE_HOST=127.0.0.1. Add Google client settings only from the password manager. Register http://localhost:3000/members/auth/google_oauth2/callback in the Google client for local sign-in. Do not copy the production DATABASE_URL into this environment.
  3. Install dependencies and prepare the local database: 
    bundle install
bundle exec rails db:create db:migrate
bundle exec rake system:bootstrap EMAIL=owner@tamu.edu FIRST_NAME=First LAST_NAME=Last
bundle exec rails server
  4. Open http://localhost:3000. Use Ctrl+C in the terminal to stop the server. Local development and test databases are pt502_development and pt502_test; automated tests can erase the latter.

Backups and importing existing data

The supported system transfer here is a complete PT-502 PostgreSQL database, including its schema and ledger. It is not a spreadsheet append. It replaces the target database. Keep the source intact and test in an empty staging database first. Data from a different app or schema needs a reviewed conversion; do not paste rows into live tables.

Capture and check a backup

heroku pg:backups:capture --app YOUR-SOURCE-APP
heroku pg:backups --app YOUR-SOURCE-APP
heroku pg:backups:info b123 --app YOUR-SOURCE-APP
heroku pg:backups:download b123 --app YOUR-SOURCE-APP

Replace b123 with the completed backup ID shown by the list. Check that it is finished and belongs to the intended database. Store the downloaded dump in the organization’s protected backup location.

Restore into a staging app

  1. Deploy the reviewed compatible PT-502 code into YOUR-STAGING-APP. Confirm the staging app and source backup ID with another officer.
  2. Put staging in maintenance mode and restore the full named backup. The confirmation is intentional because existing target records will be replaced: 
    heroku maintenance:on --app YOUR-STAGING-APP
heroku pg:backups:restore YOUR-SOURCE-APP::b123 DATABASE_URL --app YOUR-STAGING-APP
heroku pg:backups --app YOUR-STAGING-APP
heroku pg:backups:info r123 --app YOUR-STAGING-APP
heroku run "bundle exec rails db:migrate" --app YOUR-STAGING-APP
    Replace r123 with the restore ID. A restore replaces migration history too, so run migrations again before using newer code.
  3. Compare the source and target counts for roles, members, events, attendances, points, requirements, and event submissions with the report below. Spot-check a member’s point-type totals and phone consent, a completed check-in, and a reviewed request. A matching count alone is not enough.
  4. If all checks pass, disable maintenance with heroku maintenance:off --app YOUR-STAGING-APP and test normal sign-in using staging’s Google callback.
  5. Before a production transfer, stop member writes, back up the existing production database, and record that rollback backup ID. Capture the final source backup while source writes are also paused. Repeat the tested whole-database restore against the confirmed production target. Do not allow new writes until counts, spot-checks, migrations, and sign-in pass.
heroku run "bundle exec rails runner 'puts({members: Member.count, events: Event.count, attendances: Attendance.count, points: Point.count, requirements: Requirement.count, submissions: EventSubmission.count, roles: Role.count}.inspect)'" --app YOUR-STAGING-APP

For a local PostgreSQL source, Heroku documents pg:push and custom-format dump imports. heroku pg:push LOCAL_DATABASE DATABASE_URL --app YOUR-STAGING-APP requires local PostgreSQL tools and an empty target. Do not run pg:reset on production to satisfy that condition. For an existing spreadsheet, agree a conversion and validation plan before any import; the app does not currently offer a spreadsheet import screen.

Schedule routine backups

heroku pg:backups:schedule DATABASE_URL --at "02:00 America/Chicago" --app YOUR-APP
heroku pg:backups:schedules --app YOUR-APP
heroku pg:backups --app YOUR-APP

Verify recent scheduled backups rather than assuming the schedule succeeded. Keep a protected downloaded copy before major changes and rehearse restore in staging. See Heroku PGBackups for plan retention limits and status commands.

Failed import and deployment recovery

An import stops partway

  1. Keep the target in maintenance mode. Do not use it or append the same data again.
  2. Use heroku pg:backups and heroku pg:backups:info r123 with the target’s explicit --app to find the failed restore and its error. Check the source backup, target database space, permissions, and schema compatibility.
  3. Retry the same complete verified backup after fixing the cause. A full restore replaces the target rather than adding a second copy, so do not try to resume by importing only “missing” rows. The report and spot-checks above show what is absent or wrong.
  4. If the transfer cannot finish, restore the target’s recorded pre-import backup with heroku pg:backups:restore b123 DATABASE_URL --app YOUR-APP, using the actual rollback ID and target. Run compatible migrations, verify the recovered records, then turn maintenance off.

A full database restore can discard writes made after its backup. That is why both write traffic and the target app must stay paused during transfer. Restore only a trusted club backup, and keep a record of each attempt’s IDs and result.

A deployment breaks the website

  1. Open Activity and logs. If the build or release failed, the previous successful release normally remains active; inspect the failure before doing anything to the database.
  2. If the new release is active and broken, turn on maintenance. Use heroku releases --app YOUR-APP to identify the last working release, such as v42, and record the current release and backup ID.
  3. Check whether that old version can use the current database schema. Heroku rollback does not undo database migrations or restore lost data. Do not run a guessed database rollback or db:reset.
  4. For a compatible previous version, run heroku rollback v42 --app YOUR-APP. Replace v42 with the verified working release. The rollback also restores that release’s Config Vars, so check the database attachment and Google client settings.
  5. Test /up, login, points, and a normal page. Turn maintenance off only when healthy. Record the release, fix the cause through a reviewed PR, and deploy the corrected commit; a rollback is a temporary recovery.

If old code cannot use the migrated schema, keep maintenance on and use a reviewed compatible fix. Restoring an earlier database backup requires a deliberate decision about newer writes that would be lost. See Heroku release and rollback behavior.

Common setup failures

Google shows redirect_uri_mismatch
Compare the exact callback URI to apps:info’s Web URL plus /members/auth/google_oauth2/callback, including https and hostname. Check both Google client settings and the app’s client Config Vars.
The app cannot decrypt credentials or will not start
Check that RAILS_MASTER_KEY matches this checkout’s encrypted credentials. Check the current logs, web dyno state, and successful release. Do not post key values in a support message.
Database connection or missing-table errors
Check Postgres availability, DATABASE_URL attachment, and the release-phase migration result. After restoring an older backup, rerun migrations for the intended code version.
A deploy reports a Ruby or dependency failure
Use the repository’s .ruby-version and Gemfile.lock, then inspect the build log. Do not upgrade versions blindly on production to bypass an error.

Practice, handover, and keeping docs current

Allow about 30 minutes for orientation, plus time for a staging deployment and restore. Use fictional test data, never a live production import as a first exercise.

  1. Have the next owner find the organization’s app, Web URL, deployed commit, current plans, and last successful backup.
  2. In staging, deploy a reviewed version, sign in as Member and Manager, and locate each guide.
  3. Capture a test backup, restore it to a designated staging target, compare the report, and verify a point total and phone-sharing choice. Explain how a failed restore is retried without appending rows.
  4. Identify a known compatible older staging release and rehearse code rollback. Explain why this does not reverse database changes.
  5. Record ownership, the successful release and backup IDs, the planned costs, and any unresolved issues in the private handover record.

After every website update, follow docs/help-maintenance.md: walk through changed features, refresh fictional screenshots, check every help route and anchor, and update the checked date. Member and officer app training stays free of hosting content. Include documentation changes in the same reviewed PR as the feature change.
